### 배경

* 프로젝트는 `davinci-ragllm`(Application 모듈)과 `davinci-core`(Core 모듈)의 **계층형 구조의 멀티모듈**로 설계되어 공통으로 사용하는 핵심 도메인 로직과 인프라 의존성은 `davinci-core`에, 각 서비스별 정책과 애플리케이션 로직은 `davinci-ragllm`에 위치해 있다.
* 인증/인가는 하위 모듈인 `davinci-core`에서 Spring Security를 기반으로 구현돼 있으며, 기본 인증 주체인 `user`참조하는 형태로 설계되어 있다. 
* 기획상 해당 애플리케이션에서 **새로운 인증 주체**가 필요해졌고 상위 모듈(`davinci-ragllm`)에서 구현해야 했기 때문에 기존 구조로는 확장이 어려운 상황이었다.

### 구조 파악 및 문제 분석

#### 구조적 문제
- **상위 모듈 접근 불가:** 인증 관련 컴포넌트가 모두 하위 모듈(`davinci-core`)에 위치하고 있고 *인증저장소에 접근하는 컴포넌트에서 직접 인증 주체 클래스를 참조해야만 하는 구조*로 인해, 상위 모듈에 새롭게 추가해야 하는 인증 주체를 참조할 수가 없었다.
	
- **인증 주체(`user`)에 대한 강한 결합:**  인증 컴포넌트가 특정 인증 주체에 강하게 의존하고 있어, 새로운 인증 주체를 추가하거나 교체할 때 컴포넌트 내부 로직 전체를 수정해야 한다. 즉, 확장성과 유연성이 저하된 설계로 인해 다른 인증 주체를 쉽게 추가하거나 인증 정책을 변경할 수 없었다.
	
	![[Pasted image 20260109173247.png]]
	
#### 데이터 정합성 리스크
- **영속성 컨텍스트 생명주기 불일치:** 인증 객체가 JPA Entity를 직접 필드로 참조하여 `ThreadLocal`에 보관함.
    - 트랜잭션 범위를 벗어난 영역(Filter 등)에서 **Lazy Loading 시 `no Session` 예외** 를 발생시킴
    - 엔티티가 다른 트랜잭션에 재진입(Merge)할 경우, **의도치 않은 Update 쿼리(Dirty Write)가 발생**하여 데이터 무결성을 위반하게 됨

### 해결

- **인증정보 관리 객체 분리:**
    - 기존 구조에서 *인증저장소(SecurityContextHolder)에 접근하는 책임의 클래스를 분리*하고, 합성을 통해 신규 인증주체 및 정책을 추가하도록 변경(상속보다 유연성과 재사용성 측면에서 유리하기 때문)
    
	![[Pasted image 20260109173315.png]]
	
	
- **JPA Entity → DTO 전환:**
    - 제네릭 구조를 변경하여 **영속성 컨텍스트와 분리된 DTO**만을 저장하도록 구조 변경.
    
    ![[Pasted image 20260109173319.png]]

### 성과

- **아키텍처 유연성 증대:** 인증저장소 접근 컴포넌트를 따로 분리하여 유연성과 확장성 향상 **(인증주체 추가시 작업 파일 수 50% 감소)**
- **데이터 안정성 확보:** 영속성 컨텍스트 이슈(LazyInitializationException, Dirty Write)를 제거하여 데이터 안정성 확보
