### 배경

관리자 페이지

### 문제
#### 기존 이슈
- **정합성 이슈:** 기존 Elasticsearch (Nori)형태소분석기에서 복합 명사가 분리되어 필터링 대상에서 누락되는 문제 발생.

#### 발견된 이슈
- **비효율적 아키텍처:** 단순 문자열 매칭을 위한 외부 통신으로 인해, 대량 트래픽 발생 시 **불필요한 네트워크 I/O 비용**과 응답 지연이 발생
        
### 원인 및 분석
- **기존 방안의 한계:** Elasticsearch 커스텀 형태소분석기의 사전 갱신 시, 인덱스의 `Close/Open` 과정이 필요하여 서비스 불안정성을 초래하고, 운영 복잡도가 높음.
        
- **기술적 의사결정:**
    - "단순 금칙어 필터링에 무거운 형태소 분석기가 필수적인가?"라는 의문을 바탕으로, **Elasticsearch 의존성을 제거하여 시스템 복잡도를 낮추는 것을 목표로 설계를 재검토**함.
            
    - 금칙어 처리하는 여러 실무 사례를 분석하였고, 그 결과 별도의 검색 엔진 없이 인메모리 방식만으로 더 강력한 성능을 낼 수 있는 **아호코라식(Aho-Corasick) 알고리즘** 도입을 최종 결정함. (참고 사례: [배달의민족 기술블로그](https://techblog.woowahan.com/15764/)))
            
### 해결
- **In-Memory 기반 필터링 구축:**
    - 애플리케이션 실행시점에 금칙어를 Trie 자료구조로 로드하여, 외부 통신 없이 고속으로 필터링 수행 (라이브러리: `org.ahocorasick`)
            
- **분산 환경 데이터 동기화:**
    - 관리자 페이지에서 금칙어 변경 시, RabbitMQ Fanout Exchange를 활용해 모든 서버 인스턴스에 변경 이벤트를 브로드캐스팅하여 실시간으로 인메모리 Trie 재구축 및 동기화 구현.
            
### 성과
- 처리속도 개선: 1,000 문장 기준 처리 시간 약 90,000ms → 50ms로 단축 

- **운영 효율성 증대:** Elasticsearch 커스텀 토크나이저 관리 및 스케줄러 로직을 제거하여 아키텍처를 단순화하고, 네트워크 비용 및 장애 포인트 최소화.
