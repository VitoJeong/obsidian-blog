
## 1. 요구사항 분석

- **기본 기능**: 고객 ↔ 상담사 간 실시간 채팅 세션 제공.
    
- **멀티 세션 지원**: 동시에 여러 상담이 가능해야 함.
    
- **통계 집계**: 상담별 메시지 수, 대화 시간 정도 등 집계 필요.
    
- **분산 환경 고려**:
    
    - 여러 대의 서버에서 API, 시나리오, NLU, 채팅 기능이 동시에 동작.
        
    - 세션이 특정 서버에 종속되지 않고, 클러스터 어디서든 상담 이어가기 가능해야 함.
        
    - 장애 시 메시지 유실 최소화.
        
- **확장 고려**: 대규모 로그 분석, 머신러닝 학습 같은 고급 기능은 당장은 필요 없음.
    

---

## 2. 기술 스택 후보 비교

### RabbitMQ (STOMP/WebSocket)

- **장점**
    
    - STOMP/WebSocket을 바로 지원 → 실시간 채팅에 적합.
        
    - 세션/사용자 단위 큐 라우팅 가능 → 고객 ↔ 상담사 매칭 단순.
        
    - 낮은 레이턴시 (ms 단위).
        
- **단점**
    
    - 메시지 영구 저장/분석에는 약함 → DB 연계 필요.
        
    - 트래픽 급증 시 확장성 한계 있음.
        

### Redis Pub/Sub

- **장점**
    
    - 단순, 빠른 Pub/Sub.
        
    - 구현/운영이 가볍다.
        
- **단점**
    
    - 메시지 내구성 없음 → 장애 시 유실 위험.
        
    - 세션 관리/라우팅은 직접 구현해야 함.
        

### Kafka

- **장점**
    
    - 대규모 확장성, 메시지 내구성, 재처리 가능.
        
    - 분석/로그 저장에 최적화.
        
- **단점**
    
    - WebSocket/STOMP 지원 없음 → Gateway 필요.
        
    - 세션 기반 라우팅 부적합.
        
    - 레이턴시 수십~수백 ms 이상 → 채팅에 불리.
        

---

## 3. 적합한 선택

- **실시간 채팅**이 핵심이고,
    
- **집계는 단순 통계 수준**이므로,
    
- **RabbitMQ + Consumer + RDB 저장** 구조가 가장 적합.
    

---

## 4. 권장 아키텍처

1. **실시간 메시징**
    
    - 고객/상담사 ↔ API ↔ RabbitMQ (STOMP/WebSocket).
        
2. **메시지 저장**
    
    - 별도 Consumer 서비스가 메시지를 DB(`chat_message`, `chat_session`)에 적재.
        
    - 저장 시 메시지 수 증가, 대화 시간 갱신.
        
3. **통계 조회**
    
    - DB에 누적된 값 활용 → 실시간 모니터링과 사후 리포트 모두 지원 가능.
        

---

## 5. 트래픽 증가 시 고려사항

- **RabbitMQ 확장성 한계**
    
    - 기본 클러스터링(Classic Queue)은 큐 데이터가 특정 노드에만 존재 → 큐 단위 처리량이 단일 노드 성능에 제한됨.
        
    - Quorum Queue는 내구성·가용성 보장은 뛰어나지만, 합의 기반 구조로 성능이 Classic Queue보다 낮음.
        
- **확장 전략**
    
    - **중소규모(수백~수천 동시 세션)** → RabbitMQ 클러스터로 충분히 대응 가능.
        
    - **대규모(수만 이상 동시 세션)** → RabbitMQ만으로는 병목 발생 가능 → Kafka + WebSocket Gateway 구조 고려 필요.
        
- **의사결정 기준**
    
    - 실시간성·세션 라우팅 단순성이 최우선 → RabbitMQ.
        
    - 초대규모 확장성·로그 재처리가 필요 → Kafka 보조 도입.
        

---

## 6. 결론

- **RabbitMQ 중심 아키텍처**가 현재 요구사항(실시간 채팅 + 단순 통계 집계)에 최적.
    
- 트래픽이 중규모 수준까지는 클러스터링 및 Quorum Queue로 안정성 확보 가능.
    
- 향후 수만 세션 이상으로 확장할 가능성이 있다면 Kafka 기반 아키텍처를 보조적으로 준비하는 것이 바람직.
